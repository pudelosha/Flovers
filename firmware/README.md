# Flovers universal ESP32-C3 firmware

IoT Phase 3 adds universal source bundles; generated/emailed DIY sketches remain
supported. Both reuse `backend/readings/codegen.py` for sensors, payloads, TLS,
manual receipts, backend automatic claims, persistent cooldown and cycle policy.
No separate pump implementation exists. These tools never upload or run firmware.

## Hardware and generation

Olimex ESP32-C3-DevKit-Lipo: C3, 160 MHz, 4 MB, USB CDC enabled. Pins remain SDA
**9**, SCL **8**, soil ADC **3**, active-HIGH relay **4**. Relay LOW is set at the
beginning of setup, before provisioning. No new BOOT/setup button is required;
GPIO9 stays SDA. Do not press BOOT while the sensor bus is in use.

Pinned dependencies: Arduino CLI 1.6.0, ESP32 3.3.12, BH1750 1.3.0, BME280 2.3.0,
BusIO 1.17.4, Unified Sensor 1.1.15, ArduinoJson 7.4.2, Crypto 0.4.0. The lock in
`ci/toolchain.lock.json` includes archive checksums. BLE/Security1 is Espressif's
implementation; Ed25519 comes from Crypto.

```sh
python firmware/build_universal.py --backend https://api.example.com --output /tmp/sensors/flovers_universal
python firmware/build_universal.py --backend https://api.example.com --output /tmp/pump/flovers_universal --pump
```

Universal needs the 3 MB app partition without OTA:

```text
esp32:esp32:esp32c3:CDCOnBoot=cdc,CPUFreq=160,FlashSize=4M,PartitionScheme=huge_app
```

BLE/TLS exceeds the old 1.31 MB app slot. DIY keeps `PartitionScheme=default`.
Both vendor layouts keep NVS at `0x9000`, size `0x5000`; universal changes app/SPIFFS
allocation. Do not blindly flash partition tables over existing devices or erase
NVS. Physical factory flashing needs a separately reviewed procedure. No OTA exists.

## Unique factory records

An empty universal board refuses operation without its unique factory NVS identity.
The binary contains no customer Wi-Fi password, account secret, bootstrap seed or
device token. `factory/create_identity.py --output <new-directory-outside-git>`
generates a random Ed25519 seed and independent 256-bit BLE PoP, private factory
JSON/NVS CSV, public enrollment JSON and QR JSON. Files are exclusive, mode 0600,
in a 0700 directory where supported. Windows operators must additionally enforce
restricted NTFS ACLs; POSIX modes alone do not protect Windows key custody.

The factory CSV uses namespace `flovers-factory`, key `identity`, JSON string data.
Use the matching Espressif NVS partition generator in an approved factory workflow.
Upload **only** `public-enrollment.json` to Django's operator-only
`enroll_physical_device` command. Never upload the seed/PoP to Django or Git, or print
them in logs. No real identities are generated by tests; their records are synthetic.

QR schema for the later mobile parser:

```json
{"version":1,"type":"flovers-device","hardware_id":"FACTORY_TEST_0001","name":"FLOVERS_EST_0001","transport":"ble","pop":"unique-random-local-proof-of-possession"}
```

BLE name suffix is the hardware ID's last eight characters. The QR contains a local
possession secret, **never** a long-term backend token or account secret. Protect the
sticker. MAC addresses are not authentication.

## Provisioning and recovery

Every power-on opens an approximately five-minute BLE window; a currently processing
operation can extend it by bounded network timeouts. Power cycling permits recovery
and Wi-Fi changes without extra buttons or erasing identity/safety. There is no
insecure remote setup command. Use Espressif protocomm **Security1 with the unique,
nonempty PoP**. UUID bytes are in `FloversUniversal.h`. Custom endpoint:
`flovers-config`. Standard `prov-config` and `prov-ctrl` are removed to prevent
unvalidated Wi-Fi commits/resets. Security negotiation stays Espressif's protocol;
the app must use its custom-endpoint API, not stock immediate Wi-Fi apply. No SoftAP.

Commands inside the authenticated channel:

- `action=status`: bounded status and hardware ID, no secrets.
- `action=pair`: `ssid`, `password`, `session_id`, `claim`, `proof_payload` from
  Django's authenticated start response. Firmware validates scope and claim digest,
  signs exact decoded bytes, and contacts its fixed backend over verified HTTPS.
- `action=wifi`: `ssid`, `password`; requires a local credential and preserves
  hardware ID, binding, token and all pump safety records.

Mutations enter one pending-command queue; network/NVS work runs outside the BLE
callback. Accepted means **queued**, not paired. Poll owner-only Django pairing and
configuration status before showing success. BLE/Wi-Fi connectivity is insufficient.
The mobile Phase 4 wizard uses this endpoint; see
[mobile pairing](../docs/devices/MOBILE_BLE_PAIRING.md). Status includes `in_progress`
from the command guard, an `operation_id` correlation value and a separate
`operation_state` outcome. Wi-Fi reconfiguration must not accept an old `configured`
state, another operation's result, or ordinary background synchronization after a
failed candidate network. The correlation value is not an authentication credential.

Wi-Fi driver credentials use RAM storage. Candidates are tested before replacing
the previous NVS record; failures restore the previous in-memory network. Binding,
runtime and network are persisted before final runtime acknowledgement. Factory,
binding, network, runtime and existing pump safety use separate namespaces. Each
record is one checksummed NVS value with read-back verification. Unchanged data is
not rewritten each minute. Runtime snapshots carry a token digest to reject another
binding's version counter after an authorized rebind.

Interrupted NVS writes can lose the value being written. Missing/corrupt identity,
token or configuration fails closed, without erasing storage. Retry Wi-Fi in the
next boot's BLE window. If a credential was issued but not durably stored, the owner
must revoke/unbind in Django and start again; no plaintext token recovery exists.

Desired runtime configuration is polled every minute and validated: version/digest,
sensors, interval 1–1440 min, pump duration 1–300 sec, cooldown 1–32767 min, threshold,
capability and mandatory backend/offline safety flags. Persist/apply precedes exact
acknowledgement. Disabled configuration is acknowledged but cannot run cycles. A
reboot requires a fresh backend exchange before watering; network/ack failures block
cycles until recovery. Physical cooldown survives logical rebinding. Pairing/Wi-Fi
work keeps relay LOW, never clears receipts/cooldown and never enables automatic
watering. Defaults remain 60 min / 20 sec / 60 min, automatic OFF. No offline watering.

## Security and verification limits

Checksums detect corruption; they are not encryption. Ordinary NVS is vulnerable to
physical flash readout. Commercial manufacturing must separately establish secure
boot, flash/NVS encryption and key custody. No eFuses are burned and raw NVS is not
claimed confidential. TLS root rotation follows `backend/readings/TLS.md`.

CI requires real compilation of both DIY and both universal variants, preserving the
existing C++ host pump/payload checks. Compilation/source tests do not prove BLE
interoperability, available runtime heap or real power-cut behavior. Before physical
rollout test Android/iOS, repeated reconfiguration, cancellation/timeouts, power cuts
at each NVS write, revoked credentials, flash wear, sensor faults and relay startup
on actual C3 hardware. No hardware testing or flashing is claimed in this phase.
