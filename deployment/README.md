# Backend rollout configuration

The checked-in `docker-compose.yml` is a development stack. The deployment workflow uses `/opt/app/docker-compose.prod.yml` on the VPS; that file and the live proxy configuration are not in this checkout. A [read-only VPS inspection on 2026-10-15](VPS_CHECK_2026-10-15.md) confirmed host Caddy with a loopback backend and identified the remaining production configuration changes. No production deployment or configuration changes were performed during that inspection.

## Runtime configuration

Copy the relevant entries from `backend.production.env.example` into the existing private runtime environment for **web, worker and beat**. Keep existing database, SMTP and Firebase settings. Do not replace an existing private signing key with an example value: changing either key invalidates its signed data/tokens. If a previously public development key was used, generate a new private key and require users to sign in again. Production is the default `APP_ENV`; both signing keys must be explicitly supplied, private and at least 32 characters. `APP_ENV=development` or `APP_ENV=test` enables development defaults only for those environments. `LOAD_DOTENV=False` uses injected environment variables without reading an image-local `.env`.

On 2026-10-15, the VPS's existing `/opt/app/.env` was configured with a new random JWT signing key and restricted to mode `0600`. Compose verification confirmed that web, worker, and beat will share it without changing other settings. It activates when the next deployment recreates the containers; no restart was performed during configuration. Preserve this key on subsequent deployments. See the [inspection follow-up](VPS_CHECK_2026-10-15.md).

`EMAIL_TIMEOUT` defaults to 30 seconds and accepts 1–120 seconds, keeping an individual SMTP operation bounded below the notification delivery lease. Configure `THROTTLE_CACHE_URL` to a shared Redis database, such as `redis://redis:6379/2`, for all web workers. Its database must be distinct from Celery's broker/result databases. Without it, Django's local memory cache applies quotas separately in each process; DRF throttles also use non-atomic cache operations and are not a strict distributed admission limit.

The Docker build context excludes `.env` files and the `secrets` directory. Mount credentials at runtime, preserve restrictive permissions and keep secrets outside the repository. Existing images may still contain previously copied credentials; rebuild and rotate any credentials that were exposed.

## Choose the existing proxy topology

**Caddy on the host:** use `Caddyfile.example` as the reverse-proxy portion of the existing site. Publish the backend only as `127.0.0.1:8000:8000`. The peer address seen inside Docker may be the Docker bridge gateway rather than `127.0.0.1`; inspect the socket peer in the actual deployment, then set `TRUSTED_PROXY_CIDRS` to that exact address (`/32` for IPv4, `/128` for IPv6). Do not assume a bridge subnet or trust all private addresses. The example overwrites forwarded identity headers with Caddy's direct client address and TLS scheme. If a CDN or another proxy precedes Caddy, explicitly configure that separate trust chain before preserving its client identity. See [Caddy's reverse proxy documentation](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).

**Traefik in Docker:** adapt `traefik.compose.example.yml` to the deployed Traefik service, existing HTTPS/certificate configuration and an unused dedicated subnet. The example fixes Traefik's peer to `172.29.0.2` and trusts only that address. Replace the backend's existing `ports` section with no published port; adding a second Compose file can merge an old published port back in. Connect the backend to its existing database/Redis network as well as the proxy network. Do not enable `forwardedHeaders.insecure`; configure `forwardedHeaders.trustedIPs` only if there is another explicitly trusted upstream proxy. See Traefik's [entry point trust settings](https://doc.traefik.io/traefik/reference/install-configuration/entrypoints/) and [Docker routing configuration](https://doc.traefik.io/traefik/reference/routing-configuration/other-providers/docker/).

For either topology, expose only the intended proxy's HTTP/HTTPS ports publicly. Keep PostgreSQL, Redis, MailHog and the backend private; the checked-in development stack now binds their published ports to loopback. A physical development phone needs an explicitly chosen LAN bind address (`BACKEND_BIND_ADDRESS`) and appropriate local firewall access. Docker-to-Docker clients continue to use service names rather than those host bindings.

The backend discards forwarded IP and TLS headers from untrusted socket peers. With no `TRUSTED_PROXY_CIDRS`, requests are safe from forwarded-header quota spoofing, but proxied callers share the proxy's quota and HTTPS recognition is unavailable. Through a trusted peer, the backend walks `X-Forwarded-For` from the right and stops at the first untrusted address. Every trusted proxy must overwrite or correctly append verified identity headers and prevent clients from bypassing it. Do not set `TRUSTED_PROXY_CIDRS=0.0.0.0/0` or `::/0`.

## Automatic backend deployment

Pushes to `main` affecting the backend, Compose file, deployment scripts, or backend workflow build and deploy automatically. The workflow runs the deployment tests before building, and serializes backend releases so two deployments cannot migrate at the same time. Android and website release behavior is unchanged.

The workflow sends `deploy_backend.py` to the VPS over the existing SSH connection. Using `/opt/app/docker-compose.prod.yml` and its existing private runtime environment, the script:

1. Identifies the Django service and related application services using `ghcr.io/pudelosha/flovers`.
2. Pulls the triggering commit's image and pins its registry digest for both migrations and application startup.
3. Runs `python manage.py check --tag models` before downtime, then stops the matching application services, including Celery workers and beat. This lightweight settings/model check avoids loading another recognition model beside the live application on a small VPS. Database, Redis, and proxy services stay running.
4. Runs `python manage.py migrate --noinput` once in a temporary container with the production service's environment, network, and mounts. Django runs its full system checks, including URL and recognition-model loading, before applying migrations; the old application has released its memory by this point. Its entrypoint is overridden so an external startup script cannot start a server instead. Temporary check/migration containers have Traefik routing disabled.
5. Starts the application services using the same pinned image and waits up to 120 seconds for running containers or their configured health checks. This does not replace an HTTP check through the public proxy. Unused image pruning happens only after successful startup.

The VPS needs Python 3.8+, Docker Compose with `up --wait --wait-timeout` support, and its existing GHCR pull credentials. PostgreSQL and Redis must already be running. The Django service is normally detected as `web`, `backend`, `api`, or `django`, or from a unique non-Celery application command. If detection is ambiguous, set the GitHub repository variable `BACKEND_SERVICE` to its actual Compose service name. All web/worker/beat writers must use the same backend image repository to be included; differently packaged or external writers require separate coordination. Optional profile services are included only when already running or explicitly selected as the Django service.

Before the first rollout of the security changes, apply the runtime configuration above and keep a current database backup. Subsequent pushes automatically apply every pending migration, including earlier unapplied migrations; no separate server migration command is needed. There is brief backend downtime during migration/startup.

A pull or settings-check failure leaves the current application running. A stop, migration, or startup failure fails the workflow and prevents subsequent deployment steps. In particular, failed migrations do not restart old application writers against a potentially changed schema; the backend can remain unavailable until the failure is resolved and the workflow is rerun. Migrations are not automatically reversed. Identity collisions described below are an example of data that needs an operator decision before retrying.

## Migrations and compatibility

`accounts.0002_email_case_insensitive_identity` first checks trimmed, lowercase identities. If accounts collide, it aborts with their account IDs before changing any email or deleting/merging any account. Resolve ownership and assign distinct addresses through an audited operator procedure, then retry. With no collisions, it normalizes existing emails and installs a database `Lower(email)` unique constraint. New registration and email changes normalize identities and return HTTP 400 when another request wins a uniqueness race. Do not run mixed old/new account writers across this migration.

`plant_instances.0005_plant_creation_receipts` adds durable creation receipts. Updated clients send one UUID `creation_key` per draft to `POST /api/plant-instances/`. The first successful transaction returns 201; an identical normalized retry returns the original result with 200 and creates no additional plant/reminders. Reusing the key with changed data returns 400; retry the original data or start a new draft/key. A deleted original plant cannot be resurrected by replay. Existing clients that omit the key remain accepted, but do not gain retry deduplication. Receipts, plant creation and generated reminders commit together. Receipts are retained until the account is deleted; any future retention policy must preserve the intended retry window.

Deploy the corresponding mobile update for logout/push and creation retry behavior. XLSX text exports now preserve application strings as literal cells and remove XML-invalid control characters; formula-looking names and notes do not execute as workbook formulas.

## IoT firmware rollout

Regenerate and reflash devices to obtain the new retry, automatic pump claim, timing and TLS behavior; backend deployment alone cannot update installed firmware. Current generated firmware verifies HTTPS server certificates, requires a valid clock and includes the bundled Let's Encrypt ISRG Root X1/X2 trust anchors. For an issuer outside that trust chain, configure `IOT_TLS_CA_CERT` with the appropriate trusted CA PEM before generating firmware. Keep ingest/feed/pump URLs HTTPS. Do not disable certificate validation as a workaround for an incorrect clock or CA.

New firmware explicitly advertises manual task retry support and records manual execution receipts in flash. Automatic pump execution requires the new backend claim/cooldown protocol and an explicit compatible-firmware flag; legacy automatic behavior requires regeneration/reflash. Keep the matching firmware/backend rollout and existing device credentials coordinated. The default per-device quotas are ingest 60/hour, feed 120/hour, pump polling 120/hour and pump completion/claim 120/hour; invalid unauthenticated requests remain subject to the anonymous quota.
